# task — durable shared per-task brain

A task forgets nothing it was told. The `.tasks/` **folder is the source of truth** (the 90%: goal, fundamentals, timeline, learnings — read/write-hot, git-trackable, every CLI can `cat` it). The spine DB + brain-API hold a thin **index/event mirror** (the 10%) so agents in other tabs, CLIs, and machines discover the task and see its timeline. File writes always succeed locally; the brain bridge is best-effort and degrades to braind's outbox — never a silent no-op.

The CLI: `python3 <skill>/scripts/task.py <subcommand>` (alias it as `task`). Run from anywhere inside (or above) a project; it walks up to find `.tasks/`, or scaffolds one in CWD.

## When to use it
- Any work that spans **more than one session** or **more than one agent**.
- Before spinning up an orchestrator + workers on one thing — give them a shared `.tasks/TASK-NNNN/` so the Codex in tab 3 and the MiniMax in tab 5 see each other's progress.
- The moment you're about to re-derive something a past session already knew — that's a missing `fundamentals`/`learnings` entry.

## Subcommands
```
task init "Goal title" [--domain ui --category feature --priority high]
                       [--parent TASK-0007]   # inherit parent's learnings into this task's fundamentals
                       [--desc "definition of done"] [--evidence file:line] [--deps TASK-1,TASK-2]
task claim  TASK-0042 [--by agent-name]       # ATOMIC: only an unowned task can be claimed; 2nd claimer is rejected
task log    TASK-0042 "tested ingest — 200"  [--action tested]   # append to the timeline (done|tested|blocked|handoff|note)
task learn  TASK-0042 "the real constraint is X"                 # append a distilled learning (carry-forward fuel)
task update TASK-0042 --status completed       # move lifecycle (folder follows status)
            [--add-truth "path|what"] [--add-fundamental "..."] [--add-pointer "..."] [--verified true]
task check  [TASK-0042]                         # GATE: every promised "Next: …" must have a tracked counterpart
task render TASK-0042                           # regenerate the human-readable task.md from task.json
task recall [--q "query"] [--by agent]          # cross-agent discovery via brain-API (BLOCKED, never fake-empty, if down)
task show / list [--status …]
```

## The file format (`.tasks/<status>/TASK-NNNN/`)
- `task.json` — the source of truth (schema: `templates/task_schema.json`). Key fields beyond the basics:
  - `fundamentals[]` — invariants that don't change run-to-run. **Read first when cold.**
  - `locations_of_truth[]` — `{path, what}`: where the real state for this task lives.
  - `context_pointers[]` — cheap re-entry hooks (file:line, grep terms, prior task ids).
  - `execution_log[]` — **append-only** timeline (`{timestamp, action, by, notes}`). The journal of done/tested/learned. Never rewrite; only append.
  - `learnings[]` — distilled, promotable findings with `source_task_ids` provenance.
  - `parent_task_id` / `root_task_id` — explicit lineage (never reconstruct by guessing).
- `task.md` — auto-rendered human/agent-readable view (GOAL · FUNDAMENTALS · LOCATIONS OF TRUTH · CONTEXT POINTERS · PLAN · TIMELINE · LEARNINGS). Regenerated by `render`; don't hand-edit.

## The cross-agent model (how N agents share one task)
1. The orchestrator runs `task init` → creates the file + mirrors a `created` event to the spine via `siso-brain timeline`.
2. Each worker runs `task claim TASK-NNNN --by <its-name>`. The claim is **atomic** — the second worker to try is rejected, so two agents never silently both "own" it.
3. Workers `task log` / `task learn` as they go. Every event mirrors to the spine (over tailnet to the centralized Mini brain), so any agent on any machine can `task recall` to see what exists and what's been done.
4. A child task `task init --parent TASK-NNNN` inherits the parent's learnings into its fundamentals — the next task starts warm, not cold.

## Lineage (carry-forward)
`--parent` copies the parent's `fundamentals` + distilled `learnings` into the child's `fundamentals`, sets `parent_task_id`/`root_task_id`, and records the inheritance in the timeline. Subtasks can use dotted ids (`TASK-0042.1`). Learnings carry `source_task_ids` so you always know which task produced a rule.

## Rules / traps (baked in)
- **execution_log is append-only.** The CLI only appends; never rewrite history. (Lost-update + interleave is why hand-edited `progress.md` fails for parallel agents.)
- **`verified:false` until a second pass.** Put `file:line` proof in `evidence`. Unverified = candidate, not fact.
- **One registry, no side-lists.** No `MISSING-X.md`/`progress.md` — fold session audits in, then delete the seed.
- **Status is the lifecycle**, and the folder mirrors it — let `update` move the folder; don't `mv` by hand.
- **The bridge tells the truth.** "mirrored to spine (evt_…)" means braind acked with an id. "queued to outbox" means braind was unreachable — run `siso-brain drain` later. "FAILED" means the file write is fine but the index didn't update. Never assume; read the line.
- **`recall` reports BLOCKED, not empty, when braind is down** — an empty list from a live brain ≠ a dead brain.

## When NOT to use task
- **Ephemeral session handoff** (context getting full, pass the baton to a fresh agent) → `context-relay` / `session-checkpoint`.
- **The cross-domain priority board** (what's hot, max-7 initiatives) → `THE_QUEUE.md`.
- **Pipeline/agent-coordination queue** (PM → role-inbox → artifacts table) → the `task-manager` skill. `/task` is the durable per-task *memory*; task-manager is the *dispatch pipeline*. Complementary.

## Bookkeeper (absorbed 2026-07-03)

Off-thread durable state, so the main agent stays in flow. The waste this kills: an agent either (a) stops mid-flow to write up what it just decided/learned (spends scarce main-thread attention), or (b) doesn't, and the next session re-derives it. The bookkeeper is the third option — **fire-and-forget a cheap Haiku worker that does the writing for you.** MiniMax is unlimited through Bifrost, so the cost of firing it is ~nothing.

### The reflex — when to fire (this is the whole skill)

Fire the bookkeeper the INSTANT any of these happen, then keep working — never block:
- You **made a decision** with a rationale ("going with X over Y because Z").
- You **learned something durable** ("the API returns null not NaN", "load 178 is the OBS ceiling").
- You **hit a milestone** ("ingest returns 200", "folded 9 files", "blocked on auth").
- You **hit a trap / near-miss** ("importing canonical over a variant silently changed behavior").
- You formed a **key in-flight hypothesis** worth preserving ("suspect the publish loop, not prearm").

Don't overthink it — a one-line hint is enough; the worker scans the recent transcript to fill in what you didn't say. Firing too often is fine (the extractor returns `[]` for noise). The failure is NOT firing and re-deriving later.

### How to fire

**If you are Claude** — use the native sub-agent (routes through Bifrost → MiniMax automatically), no shell:
```
Agent(model:'haiku', run_in_background:true, prompt:
  "You are the bookkeeper. Read the extraction rules at
   ~/.claude/skills/task/bookkeeper/scripts/extract-prompt.txt, then apply them to:
   CALLER_HINT: <your one-liner>
   TRANSCRIPT_EXCERPT: <the relevant recent turns, or say 'scan the newest transcript at <path>'>
   Append each emitted entry as a JSON row to <repo>/.tasks/BOOKKEEPING.jsonl in the
   schema {ts,type,text,evidence,confidence,by,task:null,filed:false,filed_to:null}.
   CONSTRAINTS: write ONLY to BOOKKEEPING.jsonl, append-only. RETURN: count appended. STOP after writing.")
```

**If you are Codex / any non-Claude caller** — no Agent tool, so use the Bifrost-curl script:
```
bash ~/.claude/skills/task/bookkeeper/scripts/bookkeep.sh "we decided X over Y; hit the symlink trap"
```
It self-locates the transcript (Claude project dir or Codex rollout), calls Haiku via Bifrost, and appends rows. Fire-and-forget; safe-by-default (any failure writes nothing, exits 0).

### The intelligence split (why this works, first-principles)

**The main model judges; the worker reconciles + files.** Deciding *what mattered* is nearly free for you — you already have the context — so YOU make that call by choosing to fire and writing the one-line note. The note is a **record-instruction, not a candidate** — the worker won't second-guess whether it's worth keeping. The worker's only job (the expensive, context-polluting grind you offload) is: read the existing books, decide dup/new/update on **substance** (not topic), and write. That's why a good one-line note → reliably filed, and re-firing the same note adds nothing.

The dumb version (worker judges what's worth keeping from a transcript) was tried and rejected: a small model waffles on borderline signal and drops ~half your entries. Keep the judgment where the context is.

### What gets written (the ledger)

Per-project append-only `<repo>/.tasks/BOOKKEEPING.jsonl`, one row per entry:
`{ts, type:(decision|learning|progress|trap|thought), text, evidence, confidence, verdict:(new|update), supersedes?, by, task, filed:false, filed_to:null}`
The worker reconciles against the existing books + active task before writing — dups are skipped, a changed value gets `verdict:update` naming the old value. Append-only survives parallel writers. Reconciliation rules + worked examples live in `bookkeeper/scripts/extract-prompt.txt`. A retry-once backstop + record-instruction framing make a clear note land deterministically.

### Filing (periodic — turns the ledger into real state)

`bash ~/.claude/skills/task/bookkeeper/scripts/bookkeep-file.sh [--task TASK-N] [--dry-run]` reads unfiled rows and routes each to its real home, then marks it `filed`:
- `progress`/`thought` → `task log TASK-N "..." --action note|blocked`
- `learning`/`trap` → `task learn TASK-N "..."`
- `decision` → DECISION-LOG (or `.tasks/BOOKKEEPING-DECISIONS.md` if none)

It auto-picks the active task (newest under `.tasks/in_progress/`) or takes `--task`. Run it at task-close, on a low-frequency sweep, or by hand. Idempotent — only touches `filed:false` rows; a routing failure leaves the row unfiled for next time, never lost.

### Why this doesn't duplicate /task, lessons, or memory

It FEEDS them. The `/task` `execution_log` is append-only with an interleave-safe CLI — built for parallel writers — so a background bookkeeper is just another writer. The bookkeeper is the *capture + routing* layer on top of the sinks you already have; it invents no new store beyond the transient ledger. Full design: `~/.claude/meta-opus/BOOKKEEPER-DESIGN.html`.

### Scripts (relocated from `~/.claude/skills/bookkeeper/scripts/` to `~/.claude/skills/task/bookkeeper/scripts/`)

- `extract-prompt.txt` — extraction rules + worked examples the worker reads.
- `bookkeep.sh` — Codex/non-Claude Bifrost-curl entrypoint; self-locates transcript, calls Haiku, appends rows.
- `bookkeep-file.sh` — periodic filer; routes unfiled rows to `task log` / `task learn` / DECISION-LOG.
